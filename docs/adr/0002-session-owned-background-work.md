# ADR 0002: Session-owned background work with separate Pi children

Accepted in [#12](https://github.com/taekwondodev/dev/issues/12), with conversation-lifetime and delivery refinements in [#24](https://github.com/taekwondodev/dev/issues/24).

Run each delegated attempt in a separate Node process using the installed Pi SDK rather than embedding child sessions in the lead process. This protects the lead's event loop and gives failures and cancellation a concrete process boundary. Preserve native resources and project instructions while supplying a focused assignment in a fresh conversation; a separate process alone does not establish reasoning quality.

Keep one controller per conversation and one producer per child transcript. Confirmed tree navigation invalidates prior attempts without closing the controller; cancelled navigation preserves work. Pi owns conversation persistence and delivery receipts, while the inbox only schedules delivery. This avoids competing lifecycle or delivery databases and keeps compaction from erasing acknowledgement. Child conversations remain outside lead-session discovery and transient-result retention.

Reserve an entire outcome-delivery batch before yielding, and fence acknowledgments by that reservation so a stale inspection cannot overwrite a newer send. Pi may hold a triggered send until the next lead run ends, so that send must not prevent the next run's boundary from publishing other completed attempts. Dispatch outside Pi's deferred-send window, after all settlement handlers, rather than inside an earlier extension event.

Read-only tools and workspace admission constrain cooperating children, not arbitrary programs: neither is an OS sandbox. The process adapter is POSIX-only and cannot guarantee cleanup of arbitrary daemonized descendants.

The [workspace integration decision](https://github.com/taekwondodev/dev/issues/30#issuecomment-5797305294) keeps WorkOwner as the sole process/attempt authority. Before releasing user code, it publishes launch intent and captured process identity to WorkspaceLifecycle under a distinct workspace-use/acquisition fence. A completed attempt is not proof of workspace quiescence: the use ends only when the owned process group and every tracked descendant are observed gone, and lost observation leaves an `unknown` use that blocks the workspace independently of transient attempt retention. WorkspaceLifecycle owns the durable reservation and binding, not job progress or cancellation. Ending a conversation must not release a task reservation or start cleanup. The one exception is the user's confirmed guided release of the conversation's own task: the host stops the session's owned work through WorkOwner, waits for the authority to observe the uses gone, and only then closes the session and lets the lifecycle attempt the release; an unobserved cessation leaves everything in place.

For cancellation, delivery and recovery behavior, read [background work](../background-work.md). For lifecycle and persistence authority, read [ADR 0004](0004-authoritative-lifecycle-incremental-store.md).
