# ADR 0002: Session-owned background work with separate Pi children

Accepted in [#12](https://github.com/taekwondodev/dev/issues/12), with conversation-lifetime and delivery refinements in [#24](https://github.com/taekwondodev/dev/issues/24) and bounded nesting in [#19](https://github.com/taekwondodev/dev/issues/19).

Run each delegated attempt in a separate Node process using the installed Pi SDK rather than embedding child sessions in the lead process. This protects the lead's event loop and gives failures and cancellation a concrete process boundary. Preserve native resources and project instructions while supplying a focused assignment in a fresh conversation; a separate process alone does not establish reasoning quality.

Keep one controller per conversation and one producer per child transcript. Confirmed tree navigation invalidates prior attempts without closing the controller; cancelled navigation preserves work. Pi owns conversation persistence and delivery receipts, while the inbox only schedules delivery. This avoids competing lifecycle or delivery databases and keeps compaction from erasing acknowledgement. A coordinator's in-memory receipt index reads new raw entries as the branch grows and rebuilds when the current branch no longer extends its last observed entry; it never acknowledges an outcome from an abandoned branch. Child conversations remain outside lead-session discovery and transient-result retention.

Reserve an entire outcome-delivery batch before yielding, and fence acknowledgments by that reservation so a stale inspection cannot overwrite a newer send. Pi may hold a triggered send until the next lead run ends, so that send must not prevent the next run's boundary from publishing other completed attempts. Dispatch outside Pi's deferred-send window, after all settlement handlers, rather than inside an earlier extension event.

Nesting is one level under the same controller. A child the lead authorizes for one assignment is a coordinator: it asks the lead's controller, over its own IPC channel, to start, list, inspect and cancel leaf children. The controller binds each request to the channel it arrived on, never to an identity in the message, and remains the only authority for admission, launch, records, cancellation and observation. A controller per coordinator was rejected because it splits cancellation, quota and usage accounting across processes; unrestricted recursion because nothing would bound the attempts of a session. Leaf outcomes go to the coordinator's conversation, acknowledged from its branch as lead delivery is, and the controller rejects a coordinator's result while one of its requests is pending, a leaf is live or an outcome is unacknowledged, so completion never rests on the coordinator model's claim; the acknowledgement itself comes from dev's child runner, after the outcome is on the coordinator's conversation branch. The guarantees an operator relies on are in [work](../work.md#behavior).

A delegated prompt loads a skill through Pi's native `/skill:name` expansion, not through injected bodies or a filtered catalog. Pi expands skills on the same path that runs extension commands and prompt templates and passes an unknown skill through as text, so the child validates the invocation before the first model request and uses that path only for a verified skill.

Read-only tools and workspace admission constrain cooperating children, not arbitrary programs: neither is an OS sandbox. The process adapter is POSIX-only and cannot guarantee cleanup of arbitrary daemonized descendants.

The [workspace integration decision](https://github.com/taekwondodev/dev/issues/30#issuecomment-5797305294) keeps WorkOwner as the sole process/attempt authority. Before releasing user code, it publishes launch intent and captured process identity to WorkspaceLifecycle under a distinct workspace-use/acquisition fence. A completed attempt is not proof of workspace quiescence: the use ends only when the owned process group and every tracked descendant are observed gone, and lost observation leaves an `unknown` use that blocks the workspace independently of transient attempt retention. WorkspaceLifecycle owns the durable reservation and binding, not job progress or cancellation. Ending a conversation releases nothing by itself. Only a user's quit is followed by a sweep, and only after the session's owned work and attachment are closed; the sweep attempts a workspace only when the authority observes its uses quiescent ([ADR 0005](0005-scoped-runtime-coordination.md#release)). Signals, crashes and session replacements start no cleanup.

For cancellation, delivery and recovery behavior, read [work](../work.md). For lifecycle and persistence authority, read [ADR 0004](0004-authoritative-lifecycle-incremental-store.md).
