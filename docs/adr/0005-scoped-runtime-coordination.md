# ADR 0005: Scoped admission for concurrent dev sessions

Coordinate cooperating dev runtimes through account-wide workspace reservations and separate kernel-lock gates for installation, conversation and checkout ownership. The checkout, not the repository or runtime fleet, is the contention unit: independent work proceeds concurrently without treating a dead process's PID as ownership. This is cooperative coordination, not an OS sandbox.

Accepted sources: [scope](https://github.com/taekwondodev/dev/issues/18), [account-wide authority](https://github.com/taekwondodev/dev/issues/31#issuecomment-5798717688) and [checkout isolation](https://github.com/taekwondodev/dev/issues/27#issuecomment-5795675435). Read this record before changing admission, identity or process observation. [Workspace](../workspace.md) owns commands and recovery; [ADR 0004](0004-authoritative-lifecycle-incremental-store.md) owns durable facts.

## Gates and identity

Use separate SQLite rollback-journal lock databases rather than a global mutex or filesystem/PID registrations. Process death releases kernel locks; lock databases stay in place while a runtime may hold or claim them, because unlinking them can split ownership across inodes. Installation admission is shared by runtimes and exclusive for maintenance, independent of the data home. Conversation claims combine canonical file identity and Pi session identity, with an account-wide gate to detect competing installations and incarnation gates to distinguish ended sessions.

Installation-local conversation locks are the exception: one accumulates per conversation key, so cleanup removes them, but only under exclusive installation admission. Every such claim is taken and held under shared admission, so an exclusive holder proves none is held or being claimed. Keep that invariant when changing a lease: prepare the lock directory and stop claiming inside admission, never before or after it. Checking a lock's inode after each acquisition was rejected because it puts the proof on every claim instead of on the one rare remover. Cleanup attempts the exclusive hold beside every session start and exit, so it must stay momentary and a starting runtime waits it out instead of refusing. This does not extend to account-wide gates: no installation's admission covers their holders. [PR #308](https://github.com/taekwondodev/dev/pull/308) records the growth and the verification; [Launcher state](../launcher-state.md#automatic-history-cleanup) owns when removal happens.

The authority is account-wide because installation-local claims cannot coordinate one repository across data homes. Readers and writers share checkout presence; writers additionally hold the writer gate. Dev's structural Git effects take a repository gate, but ordinary commands must not fence every linked worktree. Acquire structure, canonical path slots, then short record transactions; duplicate slot requests coalesce to writer access if any request writes. Enumerations skip a repository whose registration has not finished, because its shard holds no records yet, and its next registration resumes it. Only that resumption waits momentarily for the structure gate: two contenders refusing without waiting would leave it unfinished, while ready repositories never wait. Publish new authority databases by exclusive rename, not a hard link, because openers refuse the transient second link.

A free gate does not prove a dead controller's descendants are gone. Durable use facts, acquisition/binding fences and physical identities remain necessary. Persist volume UUID plus lossless inode, not reboot-unstable `st_dev`. Observe each canonical directory afresh through one native file descriptor, with canonical-path and identity checks around the observation. Native observation avoids helper startup without caching volume facts; it accepts the same risk of blocking on a stalled filesystem as other synchronous checks ([PR #253](https://github.com/taekwondodev/dev/pull/253)). Refuse lookup failures or object races rather than falling back to path names. A device-to-volume cache was rejected because a remounted volume can reuse a device number ([#64](https://github.com/taekwondodev/dev/issues/64), [#177](https://github.com/taekwondodev/dev/issues/177)). Current validation remains required under the [single-schema rule](../../AGENTS.md#boundaries).

Checkout descriptions still require fresh Git reads. To avoid repeated launcher lookup, the authority may retain the Git binary resolved by `/usr/bin/git`, but only when it is the Git every checkout would select, and only for the helper-free identity read; other Git commands retain the launcher's environment setup. An `xcode-select` change takes effect for identity reads on the next launch, an accepted limit because the previous toolchain's Git describes a checkout the same way. [PR #310](https://github.com/taekwondodev/dev/pull/310) retains the comparison evidence; [the Git adapter](../../src/workspace-git.ts) owns executable selection and fallback.

## Scoped workspace operations

A shell is an opaque operation within its conversation's writer grant, occupying only that checkout. Git's own locks govern shell structural commands; dev's structure gate protects dev's structural effects. Scoped operations require an ordinary grant and cannot nest inside scoped operations or process grants. Ordinary reads fence nothing.

Writer admission and its scoped operation may share a checkout observation only for the conversation's bound workspace, within one synchronous authority request. Later reports that release user code or settle the use still observe afresh. Writer and scoped refusals remain distinct so combining admission does not change refusal messages or turn termination. One difference is accepted: a stale host may need to settle an already admitted scoped use before refusing a mismatched writer grant. [PR #310](https://github.com/taekwondodev/dev/pull/310) records the performance evidence.

Classify tool effects through the [extension policy](#executable-extensions), never by tool name alone. Authority-record operations and the host's workspace handoffs are distinct from project writes. A refusal that requests a handoff, meets a parked host or requires review must return an error result requesting termination rather than throw: a thrown error cannot request termination. Every other refused admission requests none, so the model can report its reason.

A tool-originated handoff ends the run through Pi's extension abort: a refusal alone cannot stop a batch whose sibling already ran normally. The host aborts at the refused call's execution end to preserve its reason, then waits for idle before switching. This accepts Pi's Escape-like effects instead of another request in the parked context. Keep the handoff abort separate from background-work cancellation. User-bash handoffs have no model run to end.

[#149](https://github.com/taekwondodev/dev/issues/149) records the decision and rejected alternatives; [PR #153](https://github.com/taekwondodev/dev/pull/153) retains the measurements and real-TUI evidence. [Workspace admission](../workspace-admission.md#admission-and-isolation) owns the visible handoff behavior.

A review refusal ends the run by the same abort. Its reason becomes a session entry for [presentation](0006-global-visual-layer.md), because the model never answers the refused call. A worktree allocation that fails after its Git effect started stays such a refusal for that session: nothing repairs it in place ([fenced effects](0012-workspace-release.md#fenced-effects)).

A read-only leaf inherits access to its coordinator's admitted workspace through that same attachment's process grant. It records its own use but needs no separate presence gate. This lets a writer's reviewers see uncommitted files without unrecorded participation or broader selection authority. [Bounded nesting](https://github.com/taekwondodev/dev/issues/19) records the requirement.

### Process observation

End a process use only after its group and every tracked descendant are observed gone. Polling, launch identity capture and signalling read fresh process facts, never a shared process-table snapshot. Capture identity before releasing user code and match fresh birth identities before signalling; a root group remains attributable while a member lives. Observe exit rather than stdio closure because surviving children can keep pipes open. An unacknowledged identity report may already be durable, so observe the stopped family rather than assuming launch never happened. Confirm checkout identity only for facts that release user code or settle a use; recording facts must remain possible after checkout replacement so identity validation cannot interrupt process-family tracking. [#177](https://github.com/taekwondodev/dev/issues/177) records the decision; [Workspace](../workspace-admission.md#process-uses-and-gates) owns replacement outcomes.

Detachment before observation can escape tracking, including Pi shells starting new sessions. This risk is accepted instead of marking every shell unknown. Once observation is lost, `unknown` is absorbing: later reports or host transitions cannot settle it, and a grant cannot settle while a dependent operation is live. The [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185) supplies no repair operation; [process uses](../workspace-admission.md#process-uses-and-gates) states what frees a blocked checkout.

A live process prevents switching or automatic isolation because moving its conversation would close owned work without confirmation. Session end and replacement stop and observe shells before closing the attachment; reload preserves observation.

## Executable extensions

The [accepted policy](https://github.com/taekwondodev/dev/issues/36#issuecomment-5815706403) trusts Pi and installed extensions rather than sandboxing arbitrary plugins. Non-project presentation, status and notification effects need no admission; trust does not exempt project writes. This accepts targeted integration maintenance instead of universal containment. [SECURITY](../../SECURITY.md) owns the trusted base, Pi folder-trust exception and extension review requirements.
