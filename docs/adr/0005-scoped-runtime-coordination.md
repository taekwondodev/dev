# ADR 0005: Scoped admission for concurrent dev sessions

Use separate SQLite rollback-journal lock databases for installation admission and individual conversations, rather than a global runtime mutex or filesystem owner registrations. Independent conversations can then proceed concurrently, while process death releases kernel locks without a PID registry or stale-owner transfer. Keep published databases in place: unlinking them could split owners across inodes.

Runtimes hold shared installation admission; setup, update and rollback hold it exclusively. Keep this barrier in checkout-local `.dev/coordination/`, independent of data-home overrides, so maintenance cannot overlook an active runtime. A conversation requires both its canonical file claim and its Pi session-ID claim within the canonical data home. Reject hard-linked files and malformed coordination layouts rather than weakening that identity boundary.

Claim resume and replacement targets before Pi opens them; release unused provisional claims after success, cancellation or failure without losing the current owner. Recent-session discovery uses Pi's internal read-only `findMostRecentSession` export to preserve native cwd/mtime selection without scanning full histories. Verify this dependency on Pi upgrades; absence fails startup rather than selecting a different algorithm.

Installation and conversation coordination remain scoped as above. The [workspace authority decision](https://github.com/taekwondodev/dev/issues/31#issuecomment-5798717688) adds a separate OS-account namespace across compatible installations, replacing only the old data-home-local writer leases. Use stable checkout-path gates: readers and writers share presence, while only a writer holds the exclusive writer gate. Repository structural gates protect shared Git metadata; acquisition order is structure, canonical path slots, then short record transactions. This preserves reader/writer coexistence and avoids serializing ordinary work in independent checkouts.

A free kernel gate does not prove that a dead controller left no descendants. Durable use facts, physical workspace identity and fresh acquisition/binding fences remain necessary before reuse. Stop incompatible older runtimes before cutover; no automatic migration or old-lease fallback is authorized. These protocols coordinate cooperating dev runtimes, not external programs, and are not an OS sandbox or a durability guarantee for unrelated stores.

The [accepted specification](https://github.com/taekwondodev/dev/issues/18) records the alternatives and scope; the [implementation report](https://github.com/taekwondodev/dev/issues/18#issuecomment-5784903898) retains measurements and verification limits. For maintenance operations, read [terminal commands](../COMMANDS-TERMINAL.md#manutenzione-dalla-cartella-di-installazione).

## Scoped workspace operations

Keep the checkout as the contention unit of the [isolation decision](https://github.com/taekwondodev/dev/issues/27#issuecomment-5795675435). A lead or background shell is an `opaque` operation within its conversation's writer grant. While it is live or `unknown` it occupies only that checkout: another writer there is isolated into a new worktree, while linked worktrees keep writing, running shells and allocating. The repository structure gate serializes only dev's own Git structural effects, worktree allocation now and removal later; Git's own locks cover a shell's structural commands as they cover any external program. A repository-wide fence was rejected because one background command left every worktree of the repository unwritable.

A shell's use ends when the process adapter records that its process group and every tracked descendant are gone, not when the shell exits. A launch that never released user code is reported as failed instead. Later admissions wait for that boundary. A conversation with a live process can neither start a workspace switch nor be isolated into a new worktree until the process is observed gone or stopped, because moving it would close its session-owned work without the confirmation the [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185) requires; the user accepted that its contended write is refused with guidance meanwhile. A switch that fails before the host acts is withdrawn with the last binding kept. Each live conversation holds an exclusive gate in the account-wide authority, keyed by its session file and ID rather than its data home, because installation-local conversation claims cannot see another installation; an attach while the conversation is live elsewhere is refused, and Pi's own session switch to it is cancelled with a notice, since Pi treats a failed switch as fatal. Winning the gate proves no host still performs the conversation's switch, so an attach withdraws a switch that never reached the host and keeps the last binding, while a started one needs review. Each opening of a conversation also holds a gate for that incarnation, and every use records it, so inspection names the uses left by ended sessions, even after their conversation is resumed, instead of trusting a checkout's shared presence. A withdrawn automatic switch leaves its new worktree reserved until a sweep finds it finished. When a session ends or is replaced, its shells are stopped and observed gone before its attachment closes; a reload keeps them. A process that detaches into a new session or group before it is observed escapes this: an accepted residual risk for this personal workflow, chosen over marking every shell `unknown`, which blocked the checkout after its first command. The user accepted the same residual for delegated children, whose Pi shell starts every command in a new session, so a background process whose command exits before the next observation also escapes. Lost observation records `unknown`, which is absorbing: no later report, observation or host transition settles it. The store's single use writer enforces that, and that a grant cannot settle while a dependent operation is live. No recovery command exists yet; the [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185) excludes repair verbs from the first version, so a checkout holding an `unknown` use stays blocked for writers until explicit recovery is specified.

A scoped operation is admitted only within an ordinary grant, never within another scoped operation or a process grant. Reads are ordinary read admission and fence nothing. A lead native write is a `native-file-write` operation carrying its exact validated destination; writes to distinct destinations proceed together, and a second write to one in flight is refused. Pi runs a call only after every hook of its batch, so dev supplies the write and edit operations and reports the start from inside them, at the first file operation under the destination, and the completion when Pi reports the call finished or the session ends; every operation re-matches its path against the admitted destination. One validator serves every file-write boundary, the authority for lead writes and the child's tool hook for delegated ones. It refuses operands whose meaning differs between it and the executor, raw `..` and Pi's path shorthand, and destinations inside a nested repository, which belong to another checkout; the authority also, at the start boundary, re-resolves every component of the destination's existing prefix, so a file or ancestor directory replaced by a link since authorization is refused. The file is opened without following a final link; an ancestor replaced between that check and the open remains the accepted window, which only a directory descriptor handed to the write would close.

Delegated children write at the coarse grain of their workspace grant: the controller validates the grant for each child IPC check and the child's tool boundary applies the shared path validator, with no per-file authority record. Recovery after an abrupt child interruption therefore cannot name the file being written; revisit this only if such interruptions become frequent.

The lead's tool gate classifies each tool by its verified effect, recorded in the host after review under the policy below, never by its name alone. Dev's own `workspace` tool reads project files, writes authority records and requests a resume through the host's rebind path, the one the `work` tool uses, so it is admitted as a read. A tool without a record is refused with a visible reason and does not end the turn. Pi asks extensions about a user `!` command in load order and takes the first answer, so a global extension that answers first would bypass dev's shell; none installed does, and step 1 of the policy covers any added later.

Known limit, accepted by the user: Pi ends a tool batch early only when every result asks to terminate. When a refused unrecorded tool precedes, in the same batch, a call that parks the host for a rebind, Pi makes one more model request in the old context. Every call in it is refused as parked, so it has no effect, but it costs a request and can show a stale reply. Aborting the agent run when the host parks would remove it; that requires starting the handoff from the aborted run's end instead of `turn_end`, and verifying in the real TUI that an extension abort is not treated as a user Escape, which also stops background work.

The `work` tool asks the authority for the lead's write grant only while it runs, after the host's tool gate, so a rebind answered there reaches the host through the work controller. The tool returns that refusal as a result that asks to terminate, and the work extension marks it an error from its `tool_result` handler: the user chose this over a thrown error, which cannot ask to terminate and so cost one more model request in the old context even for a lone `work` call. It relies on two Pi internals: the coding agent's `tool_result` adapter passes no `terminate`, and pi-agent-core keeps the tool's own (`terminate: afterResult.terminate ?? result.terminate`). Verify both on every Pi upgrade; `tests/workspace/workspace-host-session-check.ts` fails if a refused `work` call again costs a request in the old context or no longer reads as an error. A `work` call that shares its batch with calls already admitted still costs the extra request above.

Pi's session replacements are wrapped as well. `/resume`, and an import of a conversation already stored in the session directory, attach the target before Pi tears the current session down, and a refusal cancels them with a notice; a copied import whose working directory is outside any Git checkout is refused the same way. `/new`, `/fork` and an import of a copy whose working directory is inside a Git checkout attach their conversation only inside Pi's runtime factory, after teardown, so an authority refusal there still ends the session: an accepted limit, rare because it needs an authority failure or, for an import, a known checkout that was replaced or is held. While a switch is pending, every replacement is refused with a notice, and a rebind that reaches the host during a replacement, or from an attachment that is no longer active, is withdrawn instead of queued against the wrong runtime. A quit after the authority started a switch but before the host acted answers the switch `cancelled`, which is true, and waits for it to settle before the attachment closes. A fork continues in the workspace of the conversation it leaves, but as a new conversation without that conversation's task: the user chose that its first write is isolated into a new worktree from the current commit, without uncommitted files, over sharing the task. Two Pi internals support the import wrapper and are to be verified on every Pi upgrade: a stored conversation is recognized with Pi's own `resolvePath` from `dist/utils/paths.js`, which expands `~` and file URLs as Pi's import does, and a copied conversation's working directory is read as Pi opens the file: the first line that parses is the header, blank and malformed lines skipped, and a header without a working directory falls back to the process's. `tests/workspace/workspace-host-session-check.ts` fails if either changes.

Process signalling matches a fresh process table against recorded birth identities before sending a signal. The root's process-group ID remains attributable while any group member lives, even after the root exits. Wait for the shell's exit event rather than stdio closure: a surviving child may keep the pipes open indefinitely. An unacknowledged process-identity report can already be durable, so observing the stopped family is safer than declaring it never launched.

Acquire path slots in canonical path order to avoid deadlocks; combine duplicate slot requests into writer access when any request writes. Cross-repository conversation publication is recoverable, not atomic: preserve uncertain source and destination facts rather than rolling back a host transition that may already have happened. A reload invalidates Pi contexts, so delayed host handoffs retain only the session controls captured while the context was live.

## Release

The [disposable-worktree amendment](https://github.com/taekwondodev/dev/issues/42) replaces exhaustive per-file certification after workflow delivery. The workflow commits and integrates code/assets to retain, reconciles agent contributions as integrated, deliberately discarded or incomplete, and selects valuable reports for verified issue/PR publication before merge. A failed publication or incomplete contribution stops delivery and release preparation in the existing task checkpoint. The runtime knows only recorded publication facts, not unrecorded selections or historical upload timing; neither an issue closure nor an exited process establishes delivery. Do not add a parallel workflow authority to infer those meanings.

After delivery, a release decided by observable completion or by explicit confirmation may discard all remaining managed-worktree contents, including dirty intermediate edits, dependencies and forgotten files neither delivered nor selected for preservation. The user accepts that loss boundary rather than per-cache approvals or filename-driven dependency blockers. Pre-existing checkouts remain reservation-only. Git's single internal force flag implements this bounded disposal, not an authorization bypass: explicit Git locks, unsupported structural entries, changed identities and live or unknown uses still refuse removal. Never double-force, add a `--yes` or `--force` flag, prune broadly or fall back to recursive directory deletion. Stable installation coordination databases are not ordinary caches; removal must preserve their ownership boundary and refuse live or uncertain claims, including runtimes whose working project is elsewhere.

An installation's source lifetime is independent of its project's working directory. A runtime or maintenance operation loaded from a managed worktree holds that worktree's existing account-wide presence gate before opening local coordination state, rechecks its physical identity after admission, and refuses a missing source rather than recreating it. The gate lives outside the removable tree. Under exclusive removal admission, cleanup also claims the target installation's existing local gate, not the caller's, and refuses missing or malformed coordination state, including directory symlinks, instead of bypassing ownership or initializing a replacement. Holding only a SQLite gate inside the tree would be insufficient: unlinking it could let a new runtime claim a new inode. The outside gate excludes compatible starters until removal finishes. Runtime release closes local claims before releasing source presence; failed closure must not free that presence. No new authority record or storage version is needed.

The [automatic-release amendment](https://github.com/taekwondodev/dev/issues/44) lets dev release finished workspaces itself, without a command or confirmation, while keeping the gates below. Completion is decided from facts dev records or observes, never from a workflow declaration: a declaration would need a workflow rule the user rejected. A pure completion function maps the assessed facts (identity, allocation reason and base, HEAD and symbolic branch, residue counts, uses, derived target, tip ancestry, bound merged pull requests and the open release operations) to a role and either a finished rule or a retained reason; `check` prints that verdict and the sweep acts on it, so there is one source of truth. The first matching rule wins: an unverifiable identity or unresolved transition retains; a release the engine recorded as `unknown` or `review-required` retains for an explicit release; an unknown, live or abandoned use retains, and an open dev conversation bound to the workspace, whose presence gate is held, counts as a live use; a pre-existing checkout finishes as `clean-checkout` only without tracked modifications or untracked non-ignored files, and only at quit; a managed worktree whose directory is gone retains as `directory-missing` for an explicit release, unless dev's own removal of it was interrupted after it started, which the sweep observes and closes; a managed worktree without tracked changes or non-ignored untracked files and without commits outside its base finishes as `no-residue`, and so does a clean child or detached worktree whose HEAD is in the target tip; a branch worktree with commits beyond its base, clean or not, finishes as `branch-merged` when a bound merged pull request's source contains HEAD, or as `branch-in-target` when HEAD is an ancestor of the target tip; a branch worktree without own commits retains as `no-commits`; a detached child allocated for a delegated writer finishes as `child-delivered` when a merged pull request of its task strictly descends from its base, was merged after the worktree was allocated and has its merge result reachable from the tip, and the child's own commits are kept: it has none, HEAD is in the tip, or a bound pull request contains HEAD, and a retention that cannot be proven leaves it unknown; an unknown proof retains as `integration-unknown`, anything else as `not-integrated`. A paused worktree at its base is trivially integrated, which is why a branch worktree needs own commits and a child needs a pull request strictly descending from its base and merged after the allocation. A clean branch worktree would keep its commits on the branch ref after removal, but own commits that never reached the target mark work in progress, so it retains as `not-integrated` until they are delivered; a clean detached worktree finishes only when its HEAD adds no commits outside its base or the target tip, because no ref would keep them. A directory that vanished without an interrupted removal by dev is not evidence of completion: the user or a tool removed it, and only an explicit release records that absence. Pull requests are bound as before and discovered from HEAD, the allocation base, sibling HEADs and any recorded pull request. Siblings are the task's managed workspaces with own commits beyond their base, reserved or removed by a completed (phase `confirmed`) remove-worktree release, whether the user confirmed it or the sweep made it; a pull request found only through a sibling must contain that sibling's HEAD, and a sibling or containment that cannot be read leaves the proof unknown, never refuted. The target is an override recorded through the `workspace` tool, otherwise the origin remote's GitHub slug and default branch, or a non-GitHub origin's HEAD branch; no origin yields an unknown verdict. An override naming the worktree's own branch proves nothing, so it is ignored in favor of the origin. The target is derived only when an integration proof is needed, so a use or a clean worktree at its base asks the provider nothing; a recorded override is still shown, since reading it needs no provider.

The sweep is one worker operation per repository: for each task it assesses, decides through completion, and attempts every finished workspace through the release gates below, with the whole task as the bound subject list, one command ID and one budgeted GitHub reader. It runs at quit and before every managed-worktree allocation, ahead of the structure gate; at allocation it skips clean pre-existing checkouts and the allocating conversation's workspaces, and the worker pushes the receipt to that attachment for the host to show once whenever it has rows. A sweep has a time budget derived from the worker's request timeout, two thirds of it at quit and one third before an allocation (40 and 20 seconds), counted from when the host sent the request, so allocations queued behind one another in the worker do not each pay a full sweep and outlast their request timeout. Its GitHub reads stop at the same deadline. Once it is spent the sweep starts no further task or attempt and records each remaining task as `task-deferred`, which the next sweep assesses, while an attempt already under way finishes. A host-side collector calling check and release per task was rejected: it spreads the policy over two callers and needs a worker-to-host callback and a second admission decision, while the attempt status it would read from the work store is already covered, since the controller reports an attempt's use quiescent only after observing its process family gone. The release request carries the decided subjects and a recorded decider, user confirmation or completion with its policy version, and every attempt-time gate reads it unchanged; an automatic attempt additionally requires the fresh assessment under the gates to be finished, and the worker refuses an automatic decider over its release RPC. A release left in `intent` or `started` is observed and closed by the next attempt, which then proceeds afresh without a retry counter, since every attempt observes first and never replays deletions; endings recorded as `unknown` or `review-required` are never attempted automatically. Receipts and inspect name the decider. Sweeps never run at signals, crashes, launcher start or turn end, and no flag makes an explicit release unattended.

`check` and `release` keep the [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185), amended by the automatic release: `release` keeps its terminal confirmation but proceeds only when some assessment of the task is `review-required`, and `/workspace release` of the conversation's own task answers that quitting sweeps it. A check holds no gate and records nothing: it assesses each reserved workspace of exactly one task as the sweep at quit would, counting the asking conversation's own uses as ending with it, and returns, with the assessment, the subject a release must still match (reservation and workspace revisions, HEAD, a digest of index and tracked working-tree content, inventory, target tip and publications, and the evidence policy version). A release takes one workspace per call under the structure gate and then the exclusive presence and writer gates of its path slot, so every live reader, writer or controller refuses it, repeats the assessment and compares subjects; any difference, a workspace added to the task since the decision, an occupied working directory or the closing conversation's file inside the target, or a spent command ID blocks the attempt before any effect. A signal after the confirmation only withdraws the workspaces not yet attempted: the attempt in flight and the receipt are uninterruptible, so the runtime's own signal handling cannot drop the result, and the command then exits 130. The cleanup evidence recorded through the `workspace` tool is the target override and exact publication readback. The verifier does not fetch or upload; unselected residue needs no publication or regeneration proof. Publication retains secret-handling safeguards, while unsupported inventory entries remain unknown. The GitHub calls of one check or release share half the worker's request timeout (30 seconds), counted from when the host sent the request, including time queued in the worker. A sweep instead shares its own deadline (40 seconds at quit, 20 at allocation), without a separate 30-second cap. An identical read is asked once, and a slow provider yields unknown evidence; these deadlines bound provider time, not local Git work.

Quitting is the TUI's release trigger. Pi's interactive quit awaits `dispose` before exiting the process, so the host wraps the runtime's `dispose`: while the launcher's interactive race has armed it, the wrapper decides one macrotask later, resolves the quit request and never returns to Pi, leaving the continuation to the launcher. A signal handler disarms the wrapper first, so Pi's own signal shutdown, which also calls `dispose`, disposes normally and no sweep follows. The launcher then disposes the runtime, which stops the session's owned work and shells before its attachment closes, releases its installation and source claims, leaves the workspace directory, and only then runs the sweep uninterruptibly, printing the receipt and exiting 0 when every attempted workspace reached a terminal outcome and 1 otherwise. SIGINT or SIGTERM during that teardown, before the sweep starts, releases nothing and exits 130; either signal once the sweep has started lets the sweep run on, observing each attempt to its recorded outcome, and exits 130 after the receipt, where a Git step that the terminal's interrupt also reached ends as `partial` for an explicit release. SIGHUP after quit (for example, closing the terminal) instead ends dev without a receipt; the next sweep observes any interrupted attempt. A disposal failure sweeps nothing and exits 1, and so does a failure of Pi's interactive mode, whose runtime is disposed without the wrapper parking it. A sweep that does not report back leaves its outcome unknown: the launcher says so, points to `inspect` and exits 1. The quitting conversation's file is passed as occupied, so a finished worktree holding its history is kept. The guided release of the conversation's own task, its cessation wait and its handover are gone: quitting already stops the work and closes the attachment, and the sweep verifies the uses for real.

For target overrides, the worktree's own branch means its branch ref, `refs/remotes/<any>/<branch-name>`, and the destination resolved by `<branch-name>@{push}`. A GitHub override names it when its repository matches any configured remote and its branch is the worktree branch or that push branch. A differently named configured upstream alone is not its own branch: Git commonly sets the start point (such as `origin/develop` or an upstream fork's `main`) as the upstream, and that remains a valid integration target.

The evidence policy version is part of the release subject and must change when an evidence predicate changes meaning; version 4 and completion policy 2 exclude Git-ignored files from completion residue, as required by [the ignored-file correction](https://github.com/taekwondodev/dev/issues/47). Ignored files remain in the inventory, state digest and structural safety checks. Fingerprint index bytes and actual tracked file bytes or link text, not Git's diff projection: assume-unchanged and skip-worktree flags can hide edits even when file size and mtime are preserved. Stream regular-file digests from no-follow descriptors rather than buffering every tracked file or executing diff drivers. Git reads disable hooks, prompts, lazy fetching and optional locks, so assessment cannot silently fetch or execute repository hooks. Replacement refs and graft files are also disabled: a locally rewritten history view must not make an unrelated commit appear delivered to the independently bound source or target. Merged-PR evidence requires independent provider facts to agree on the exact merged source revision; a current branch tip alone cannot prove what was merged. The workspace commit may equal that source or be its proven Git ancestor, while the merge result must remain reachable from the current agreed target. This proves source-history inclusion, not semantic equivalence or delivery of dirty edits. Extra or unrelated commits are not covered; unavailable required history stays unknown. Sensitive-name heuristics at publication boundaries never certify safe content and do not prohibit disposal of unselected dependency files.

### Accepted external-process race boundary

Keep release within the participating-dev protocol, not an OS sandbox against external filesystem changes. The user explicitly accepts the residual race below for dev's personal workflow rather than adding a sandbox, global process scans or a native helper. Broader containment would add integration complexity outside that workflow; repeated pathname checks are not atomic, and descriptor-relative deletion alone cannot prevent directory ancestry from moving.

Between the final identity recheck and pathname deletion, a nonparticipating process can move a selected file's parent outside the worktree and replace the original parent path with a symlink. The deletion can then remove that same selected file outside the checkout. A subsequent `partial` receipt and retained reservation do not undo that deletion. Dev therefore does not guarantee atomic filesystem containment against concurrent external changes.

The workflow constraint is to run builds, watchers and servers through dev without detaching them from its observation, stop independently started tools before release, and avoid external edits or moves while release runs. This acceptance does not relax admission gates, cleanup evidence or per-entry rechecks, nor authorize bypassing a detected unsafe path. Revisit this decision before supporting external writers during release or promising stronger deletion containment; no broader protection is adopted here.

## Effect boundary

Dev's own coordination runs in Effect: the authority client, the lead shell, native writes, the Pi host, the launcher and background work, with typed errors and one process-observation step and retry policy shared by the shell and background work. Promises remain only where Pi calls in, namely extension handlers, the runtime factory, the session replacements (`switchSession`, `newSession`, `fork` and `importFromJsonl`) and the tool operation adapters, which run the Effect programs through the host's context, and in the synchronous SQLite engine behind the authority worker, whose RPC the client wraps. The user chose one style over a documented Promise layer, accepting the rewrite and its re-review. Pi session and native-file API errors cross back as their original defects, not translated domain errors: Pi recognizes some errors by class and owns their recovery. Workspace refusals remain typed domain failures.

## Executable extensions

The [accepted extension policy](https://github.com/taekwondodev/dev/issues/36#issuecomment-5815706403) treats Pi and known, explicitly supported extensions as a trusted base, not a sandbox for arbitrary plugins. Preserve non-project presentation, status and notification effects without unnecessary workspace admission; trust does not exempt project writes from scoped coordination. This trades universal containment and arbitrary-plugin compatibility for targeted integration maintenance suited to dev's personal workflow.

Apply that policy before enabling future extensions or updates that change relevant effects. Inspect initialization, tool/event handlers, shell execution and child processes; integrate project effects before execution, and defer or refuse project-writing initialization before it runs. A tool guard installed after loading is insufficient. Recheck changed effects rather than trusting an extension's name or previous version. Trusted-code bugs remain a residual risk; external programs remain outside the protocol.

Project resources are the user's own: the user trusts what they place in a folder's `.pi/`, so dev defers to Pi's folder trust and does not refuse or re-review project extensions and packages. Trusting a folder therefore lets its project code initialize before workspace admission. This amends the policy's refusal step for the user's own projects; a folder the user has not trusted still loads no project resources.
