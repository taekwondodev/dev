# ADR 0005: Scoped admission for concurrent dev sessions

Use separate SQLite rollback-journal lock databases for installation admission and individual conversations, rather than a global runtime mutex or filesystem owner registrations. Independent conversations can then proceed concurrently, while process death releases kernel locks without a PID registry or stale-owner transfer. Keep published databases in place: unlinking them could split owners across inodes.

Runtimes hold shared installation admission; setup, update and rollback hold it exclusively. Keep this barrier in checkout-local `.dev/coordination/`, independent of data-home overrides, so maintenance cannot overlook an active runtime. A conversation requires both its canonical file claim and its Pi session-ID claim within the canonical data home. Reject hard-linked files and malformed coordination layouts rather than weakening that identity boundary.

Claim resume and replacement targets before Pi opens them; release unused provisional claims after success, cancellation or failure without losing the current owner. Recent-session discovery uses Pi's internal read-only `findMostRecentSession` export to preserve native cwd/mtime selection without scanning full histories. Verify this dependency on Pi upgrades; absence fails startup rather than selecting a different algorithm.

The [workspace authority decision](https://github.com/taekwondodev/dev/issues/31#issuecomment-5798717688) adds a separate OS-account namespace across compatible installations, replacing only the old data-home-local writer leases. Use stable checkout-path gates: readers and writers share presence, while only a writer holds the exclusive writer gate. Repository structural gates protect shared Git metadata; acquisition order is structure, canonical path slots, then short record transactions. This preserves reader/writer coexistence and avoids serializing ordinary work in independent checkouts.

A free kernel gate does not prove that a dead controller left no descendants. Durable use facts, physical workspace identity and fresh acquisition/binding fences remain necessary before reuse. Stop incompatible older runtimes before cutover; no automatic migration or old-lease fallback is authorized. These protocols coordinate cooperating dev runtimes, not external programs, and are not an OS sandbox or a durability guarantee for unrelated stores.

The [accepted specification](https://github.com/taekwondodev/dev/issues/18) records the alternatives and scope; the [implementation report](https://github.com/taekwondodev/dev/issues/18#issuecomment-5784903898) retains measurements and verification limits. Observable behavior, commands and exit codes are in [workspace](../workspace.md).

## Scoped workspace operations

The checkout is the contention unit of the [isolation decision](https://github.com/taekwondodev/dev/issues/27#issuecomment-5795675435). A lead or background shell is an `opaque` operation within its conversation's writer grant and occupies only that checkout; linked worktrees keep writing, running shells and allocating. The repository structure gate serializes only dev's own structural Git effects; Git's own locks cover a shell's structural commands as they cover any external program. A repository-wide fence was rejected because one background command left every worktree of the repository unwritable.

A shell's use ends when the process adapter records its process group and every tracked descendant gone, not when the shell exits; a launch that never released user code is reported as failed. A conversation with a live process can neither switch workspace nor be isolated into a new worktree, because moving it would close its session-owned work without the confirmation the [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185) requires; the user accepted that its contended write is refused with guidance meanwhile. A process that detaches into a new session or group before it is observed escapes: an accepted residual risk, chosen over marking every shell `unknown`, which blocked the checkout after its first command. The user accepted the same residual for delegated children, whose Pi shell starts every command in a new session. Lost observation records `unknown`, which is absorbing: no later report, observation or host transition settles it, the store's single use writer enforces that, and a grant cannot settle while a dependent operation is live. The command contract excludes repair verbs from the first version, so a checkout holding an `unknown` use stays blocked for writers until explicit recovery is specified.

Each live conversation holds an exclusive gate in the account-wide authority, keyed by its session file and ID rather than its data home, because installation-local claims cannot see another installation. Winning the gate proves no host still performs the conversation's switch: an attach withdraws a switch that never reached the host and keeps the last binding, while a started one needs review. Each opening of a conversation also holds a gate for that incarnation, and every use records it, so inspection names the uses left by ended sessions. A withdrawn automatic switch leaves its new worktree reserved until a sweep finds it finished. When a session ends or is replaced, its shells are stopped and observed gone before its attachment closes; a reload keeps them.

A scoped operation is admitted only within an ordinary grant, never within another scoped operation or a process grant. Reads are ordinary read admission and fence nothing. A lead native write is a `native-file-write` operation carrying its exact validated destination; dev supplies the write and edit operations and reports the start from inside them and the completion when Pi reports the call finished or the session ends. One validator serves every file-write boundary, the authority for lead writes and the child's tool hook for delegated ones. It refuses operands whose meaning differs between it and the executor, raw `..`, Pi's path shorthand and destinations inside a nested repository; the authority also re-resolves every component of the destination's existing prefix at the start boundary. The file is opened without following a final link; an ancestor replaced between that check and the open is the accepted window, which only a directory descriptor handed to the write would close. Delegated children write at the coarse grain of their workspace grant, with no per-file authority record, so recovery after an abrupt child interruption cannot name the file being written; revisit only if such interruptions become frequent.

The lead's tool gate classifies each tool by its verified effect, recorded in the host after review under the [extension policy](#executable-extensions), never by its name alone. Dev's own `workspace` tool is admitted as a read: it reads project files, writes authority records and requests a resume through the host's rebind path. Known limit, accepted by the user: Pi ends a tool batch early only when every result asks to terminate, so a refused unrecorded tool that precedes, in the same batch, a call that parks the host costs one more model request in the old context; every call in it is refused as parked. Aborting the agent run when the host parks would remove it; that requires starting the handoff from the aborted run's end instead of `turn_end` and verifying in the real TUI that an extension abort is not treated as a user Escape.

The `work` tool asks the authority for the lead's write grant only while it runs, after the host's tool gate, and returns a refusal as a result that asks to terminate, marked an error from the extension's `tool_result` handler; the user chose this over a thrown error, which cannot ask to terminate. It relies on two Pi internals: the coding agent's `tool_result` adapter passes no `terminate`, and pi-agent-core keeps the tool's own (`terminate: afterResult.terminate ?? result.terminate`). Verify both on every Pi upgrade; `tests/workspace/workspace-host-session-check.ts` fails if a refused `work` call again costs a request in the old context or no longer reads as an error.

Pi's session replacements are wrapped as well. `/resume`, and an import of a conversation already stored in the session directory, attach the target before Pi tears the current session down, and a refusal cancels them with a notice. `/new`, `/fork` and an import of a copy whose working directory is inside a Git checkout attach only inside Pi's runtime factory, after teardown, so an authority refusal there still ends the session: an accepted limit, rare because it needs an authority failure or a known checkout that was replaced or is held. A quit after the authority started a switch but before the host acted answers the switch `cancelled` and waits for it to settle before the attachment closes. A fork continues in the workspace of the conversation it leaves as a new conversation without that conversation's task: the user chose isolation of its first write over sharing the task. Two Pi internals support the import wrapper and are verified on every Pi upgrade: a stored conversation is recognized with Pi's own `resolvePath` from `dist/utils/paths.js`, and a copied conversation's working directory is read as Pi opens the file (the first line that parses is the header, and a header without a working directory falls back to the process's). `tests/workspace/workspace-host-session-check.ts` fails if either changes.

Process signalling matches a fresh process table against recorded birth identities before sending a signal; the root's process-group ID remains attributable while any group member lives. Wait for the shell's exit event rather than stdio closure, since a surviving child may keep the pipes open. An unacknowledged process-identity report can already be durable, so observing the stopped family is safer than declaring it never launched. Acquire path slots in canonical path order to avoid deadlocks; combine duplicate slot requests into writer access when any request writes. Cross-repository conversation publication is recoverable, not atomic: preserve uncertain source and destination facts rather than rolling back a host transition that may already have happened. A reload invalidates Pi contexts, so delayed host handoffs retain only the session controls captured while the context was live.

## Release

The [disposable-worktree amendment](https://github.com/taekwondodev/dev/issues/42) replaces exhaustive per-file certification after workflow delivery. The workflow commits and integrates code and assets to retain, reconciles agent contributions, and selects reports for verified issue or PR publication before merge; a failed publication or incomplete contribution stops delivery in the task checkpoint. The runtime knows only recorded publication facts; neither an issue closure nor an exited process establishes delivery. Do not add a parallel workflow authority to infer those meanings.

After delivery, a release decided by observable completion or by explicit confirmation may discard all remaining managed-worktree contents, including dirty intermediate edits, dependencies and forgotten files. The user accepts that loss boundary rather than per-cache approvals or filename-driven dependency blockers. Pre-existing checkouts remain reservation-only. Git's single internal force flag implements this bounded disposal, not an authorization bypass: explicit Git locks, unsupported structural entries, changed identities and live or unknown uses still refuse removal. Never double-force, add a `--yes` or `--force` flag, prune broadly or fall back to recursive directory deletion. Stable installation coordination databases are not ordinary caches; removal must preserve their ownership boundary and refuse live or uncertain claims.

An installation's source lifetime is independent of its project's working directory. A runtime or maintenance operation loaded from a managed worktree holds that worktree's account-wide presence gate before opening local coordination state, rechecks its physical identity after admission, and refuses a missing source rather than recreating it. Under exclusive removal admission, cleanup claims the target installation's existing local gate and refuses missing or malformed coordination state, directory symlinks included. A SQLite gate only inside the tree would be insufficient: unlinking it could let a new runtime claim a new inode. Runtime release closes local claims before releasing source presence; failed closure must not free that presence.

The [automatic-release amendment](https://github.com/taekwondodev/dev/issues/44) lets dev release finished workspaces itself, without a command or confirmation, under the gates above. Completion is decided from facts dev records or observes, never from a workflow declaration, which would need a workflow rule the user rejected. A pure completion function maps the assessed facts (identity, allocation reason and base, HEAD and symbolic branch, residue counts, uses, derived target, tip ancestry, bound merged pull requests and open release operations) to a role and either a finished rule or a retained reason; `check` prints that verdict and the sweep acts on it, so there is one source of truth. The first matching rule wins: an unverifiable identity or unresolved transition retains; a release recorded as `unknown` or `review-required` retains for an explicit release; an unknown, live or abandoned use retains, and an open dev conversation bound to the workspace counts as live; a pre-existing checkout finishes as `clean-checkout` only without tracked modifications or untracked non-ignored files, and only at quit; a managed worktree whose directory is gone retains as `directory-missing` unless dev's own removal was interrupted after it started; a managed worktree without changes and without commits outside its base finishes as `no-residue`, and so does a clean child or detached worktree whose HEAD is in the target tip; a branch worktree with commits beyond its base finishes as `branch-merged` when a bound merged pull request's source contains HEAD, or `branch-in-target` when HEAD is an ancestor of the target tip; a branch worktree without own commits retains as `no-commits`; a detached child finishes as `child-delivered` when a merged pull request of its task strictly descends from its base, was merged after the allocation and has its merge result reachable from the tip, and the child's own commits are kept; an unknown proof retains as `integration-unknown`, anything else as `not-integrated`. A paused worktree at its base is trivially integrated, which is why a branch worktree needs own commits and a child a pull request strictly descending from its base. Siblings are the task's managed workspaces with own commits beyond their base, reserved or removed by a confirmed remove-worktree release; a pull request found only through a sibling must contain that sibling's HEAD, and anything unreadable leaves the proof unknown, never refuted. The target is an override recorded through the `workspace` tool, otherwise the origin remote's GitHub slug and default branch, or a non-GitHub origin's HEAD branch; an override naming the worktree's own branch (its branch ref, `refs/remotes/<any>/<branch>` or the `@{push}` destination) proves nothing and is ignored, while a differently named configured upstream remains a valid target. The target is derived only when an integration proof is needed.

The sweep is one worker operation per repository: for each task it assesses, decides through completion, and attempts every finished workspace through the release gates, with the whole task as the bound subject list, one command ID and one budgeted GitHub reader. It runs at quit and before every managed-worktree allocation, ahead of the structure gate; at allocation it skips clean pre-existing checkouts and the allocating conversation's workspaces. Its budget derives from the worker's request timeout, two thirds at quit and one third before an allocation, counted from when the host sent the request, so queued allocations do not each pay a full sweep; GitHub reads stop at the same deadline, and remaining tasks are recorded `task-deferred`. A host-side collector calling check and release per task was rejected: it spreads the policy over two callers and needs a worker-to-host callback and a second admission decision. The release request carries the decided subjects and a recorded decider, user confirmation or completion with its policy version; an automatic attempt additionally requires the fresh assessment under the gates to be finished, and the worker refuses an automatic decider over its release RPC. A release left in `intent` or `started` is observed and closed by the next attempt, which proceeds afresh without a retry counter; endings recorded `unknown` or `review-required` are never attempted automatically. Sweeps never run at signals, crashes, launcher start or turn end, and no flag makes an explicit release unattended.

`check` and `release` keep the [command contract](https://github.com/taekwondodev/dev/issues/34#issuecomment-5799183185), amended by the automatic release: `release` keeps its terminal confirmation but proceeds only when some assessment is `review-required`, and `/workspace release` of the conversation's own task answers that quitting sweeps it. A check holds no gate and records nothing; it returns, with the assessment, the subject a release must still match: reservation and workspace revisions, HEAD, a digest of index and tracked working-tree content, inventory, target tip and publications, and the evidence policy version. A release takes one workspace per call under the structure gate and then the exclusive presence and writer gates of its path slot, repeats the assessment and compares subjects; any difference, a workspace added since the decision, an occupied working directory, the closing conversation's file inside the target or a spent command ID blocks the attempt before any effect. The attempt in flight and the receipt are uninterruptible. The GitHub calls of one check or release share half the worker's request timeout, an identical read is asked once, and a slow provider yields unknown evidence.

Quitting is the TUI's release trigger. Pi's interactive quit awaits `dispose` before exiting the process, so the host wraps the runtime's `dispose`: while the launcher's interactive race has armed it, the wrapper decides one macrotask later, resolves the quit request and never returns to Pi, leaving the continuation to the launcher. A signal handler disarms the wrapper first, so Pi's own signal shutdown disposes normally and no sweep follows. The launcher then disposes the runtime, which stops the session's owned work and shells before its attachment closes, releases its installation and source claims, leaves the workspace directory, and only then runs the sweep uninterruptibly. The quitting conversation's file is passed as occupied, so a finished worktree holding its history is kept. The former guided release of the conversation's own task is gone: quitting already stops the work and closes the attachment, and the sweep verifies the uses for real.

The evidence policy version is part of the release subject and must change when an evidence predicate changes meaning; version 4 and completion policy 2 exclude Git-ignored files from completion residue, as required by [the ignored-file correction](https://github.com/taekwondodev/dev/issues/47), while ignored files remain in the inventory, state digest and structural safety checks. Fingerprint index bytes and actual tracked file bytes or link text, not Git's diff projection: assume-unchanged and skip-worktree flags can hide edits. Stream regular-file digests from no-follow descriptors. Git reads disable hooks, prompts, lazy fetching, optional locks, replacement refs and graft files, so assessment cannot fetch, execute hooks or let a rewritten history view make an unrelated commit appear delivered. Merged-PR evidence requires independent provider facts to agree on the exact merged source revision; a current branch tip alone cannot prove what was merged. This proves source-history inclusion, not semantic equivalence or delivery of dirty edits. Sensitive-name heuristics at publication boundaries never certify safe content and do not prohibit disposal of unselected dependency files.

### Accepted external-process race boundary

Keep release within the participating-dev protocol, not an OS sandbox against external filesystem changes. The user explicitly accepts the residual race below rather than adding a sandbox, global process scans or a native helper: repeated pathname checks are not atomic, and descriptor-relative deletion alone cannot prevent directory ancestry from moving.

Between the final identity recheck and pathname deletion, a nonparticipating process can move a selected file's parent outside the worktree and replace the original parent path with a symlink; the deletion can then remove that file outside the checkout, and a subsequent `partial` receipt does not undo it. The workflow constraint is to run builds, watchers and servers through dev without detaching them, stop independently started tools before release, and avoid external edits or moves while release runs. This acceptance does not relax admission gates, cleanup evidence or per-entry rechecks. Revisit before supporting external writers during release or promising stronger deletion containment.

## Effect boundary

Dev's own coordination runs in Effect: the authority client, the lead shell, native writes, the Pi host, the launcher and background work, with typed errors and one process-observation step and retry policy shared by the shell and background work. Promises remain only where Pi calls in, namely extension handlers, the runtime factory, the session replacements (`switchSession`, `newSession`, `fork` and `importFromJsonl`) and the tool operation adapters, which run the Effect programs through the host's context, and in the synchronous SQLite engine behind the authority worker, whose RPC the client wraps. The user chose one style over a documented Promise layer, accepting the rewrite and its re-review. Pi session and native-file API errors cross back as their original defects, not translated domain errors: Pi recognizes some errors by class and owns their recovery. Workspace refusals remain typed domain failures.

## Executable extensions

The [accepted extension policy](https://github.com/taekwondodev/dev/issues/36#issuecomment-5815706403) treats Pi and the installed extensions as a trusted base, not a sandbox for arbitrary plugins. Non-project presentation, status and notification effects need no workspace admission; trust does not exempt project writes from scoped coordination. This trades universal containment and arbitrary-plugin compatibility for targeted integration maintenance. The trusted base and the rule applied before enabling or updating an extension are in [SECURITY.md](../../SECURITY.md).

Project resources are the user's own: the user trusts what they place in a folder's `.pi/`, so dev defers to Pi's folder trust and does not refuse or re-review project extensions and packages. Trusting a folder therefore lets its project code initialize before workspace admission. This amends the policy's refusal step for the user's own projects; a folder the user has not trusted still loads no project resources.
