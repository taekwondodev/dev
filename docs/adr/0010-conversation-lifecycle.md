# ADR 0010: Conversation transitions and retention

Conversation deletion and conversation transitions stay under the workspace authority: deletion takes the file and conversation gates that exclude attached runtimes, replacement targets are claimed before Pi opens them where its lifecycle permits, and a transition that may have reached the host is recovered rather than rolled back.

Builds on the gates, identity and admission of [ADR 0005](0005-scoped-runtime-coordination.md).

## Conversation retention admission

[The retention decision](https://github.com/taekwondodev/dev/issues/167) keeps conversation deletion under the existing coordination and workspace authority, separate from workspace release. File and conversation gates exclude attached runtimes; shared admission with creation and navigation closes the gap before a new file receives its claim. A free gate alone is insufficient: durable recovery dependencies must be reassessed before deletion. Inventory stays outside deletion admission so a history scan does not block navigation. Counting the quota only probes conversation presence, because acquiring it publishes a durably synced incarnation gate per retained conversation on every pass; deletion still acquires it.

Cleanup runs in a one-shot process with its own installation/source claims, rather than inheriting the launcher's authority. A thread could not outlive the launcher; a daemon would add an unnecessary long-lived owner. Preference publication and temporary-file deletion share exclusion because age or a filename cannot prove abandonment. [Launcher state](../launcher-state.md#automatic-history-cleanup) owns cleanup behavior and limits; the [external-process race boundary](0012-workspace-release.md#accepted-external-process-race-boundary) still applies.

## Conversation transitions

Claim replacement targets before Pi opens them where its lifecycle permits; release unused provisional claims without losing the current owner. An account-wide gate proves no other host still performs the switch. A switch never delivered to the host can be withdrawn on attach; one already started needs review.

[Issue #323](https://github.com/taekwondodev/dev/issues/323) lets a lead join the paused task that holds its own checkout. A resumable holder is not an active one: nothing writes there, so [#28](https://github.com/taekwondodev/dev/issues/28#issuecomment-5795841426)'s refinement that a paused reservation occupies its checkout is kept by asking instead of isolating, and the answer selects the task explicitly, as that resolution requires. Joining binds the conversation to that task and takes a new acquisition in the ordinary writer transaction, without a handoff: the checkout and the Pi session stay, so there is no host transition to recover. The question is a second authorization, not a held one: the first answers with the task and records nothing, and the join carries the reservation's identity and revision, so an answer given after the reservation changed attaches nothing. The question has no timeout: one would either choose for the user, against the explicit selection, or dismiss the question and end a turn that waiting keeps. Asking at launch or attaching by matching cwd were rejected: the first interrupts read-only sessions and decides before the reservation's state at the write is known, the second is the automatic attachment that resolution rejected. [Workspace](../workspace.md#resume-paused-work) owns who is asked and what each answer does.

A switch reopens the conversation's own file, and Pi writes that file only once the conversation holds a message. For a conversation without one, the host writes the header and entries the outgoing session holds in memory, as Pi's first write would, at the point where it reopens the file for the replacement runtime, and verifies that Pi reopens them as the same conversation. Writing there, after Pi's switch and shutdown handlers ran, keeps the entries extensions append in them and writes nothing for a switch cancelled before the replacement. Writing before those handlers was rejected: it loses those entries, and after a cancelled switch it leaves a file that the session Pi kept can no longer create at its first message. A file that does not reopen as the same conversation is removed and the switch fails like any other replacement failure. Refusing to switch a conversation without messages was rejected because `/workspace resume` is most useful right after launch.

Pi's lifecycle permits resume and stored-session import before teardown, but new, fork and copied import only afterward. Authority refusal can therefore end those sessions, an accepted limit. Fork starts a new task rather than sharing write ownership. Quit cancels an authority-started switch not yet acted on and waits for settlement.

Cross-repository conversation publication is recoverable, not atomic. Preserve uncertain source and destination facts instead of rolling back a transition that may have reached the host. Reload invalidates Pi contexts, so delayed handoffs retain only controls captured while live. [Host-session checks](../DEVELOPMENT.md#upgrades) exercise these integration boundaries.
